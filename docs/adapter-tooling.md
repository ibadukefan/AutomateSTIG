# Target Adapter Development Tooling

AutomateSTIG provides deterministic development tooling for adapter candidates
and static per-target release scorecards. Neither tool changes
`content/supported-targets.json`, enables a runtime adapter, proves a live scan,
or authorizes a support or competitive claim.

## Scaffold an adapter candidate

Create the parent directory first, then choose a new target key and an absent
output directory whose final name exactly matches that key:

```bash
mkdir -p adapter-work
python3 scripts/scaffold-target-adapter.py \
  --target-key example_appliance \
  --display-name "Example Appliance" \
  --stig-id Example_Appliance_STIG \
  --stig-release V1R1 \
  --transport ssh_cli \
  --output-dir adapter-work/example_appliance
```

Target keys must match `^[a-z][a-z0-9_]{2,63}$`. The tool rejects unsafe
paths, a mismatched output-directory name, missing parents, and every existing
output directory. It creates new files with owner-only permissions and never
merges with or overwrites an earlier scaffold. The generated contract runner is
owner-executable (`0700` on Unix); other generated files are `0600`.

The bundle contains schema-versioned candidate contracts for adapter behavior,
compatibility, and coverage; positive and negative rule fixtures; malformed,
permission-denied, timeout, truncated, and unsupported-version error fixtures;
and README checklists for replay and contract tests. Every fixture begins as a
synthetic, redacted, non-executable placeholder with handoff disabled. The
compatibility matrix has no accepted tested versions, and the scaffold records
live acceptance as `not_run` and its support claim as `none`.

The scaffold also generates `tests/contract-test.json`. Execute its shared
contract from the repository root. The manifest binds the exact non-claiming
`adapter-contract.json` bytes by SHA-256:

```bash
python3 scripts/validate-adapter-contract.py \
  --adapter-root adapter-work/example_appliance
```

The generated `tests/run-contract-test.py` invokes that same shared validator:

```bash
python3 adapter-work/example_appliance/tests/run-contract-test.py --repo-root .
```

Untouched placeholders deliberately exit with status 2 and list every fixture
that is not ready. A completed fixture must bind a regular, non-symlink,
bounded artifact by SHA-256. The Finding and Not a Finding cases must produce
their shared-contract oracle in both `expected` and adapter-produced `observed`
results; malformed, permission-denied, timeout, truncated, and
unsupported-version cases must produce a collection error, no evaluation
outcome, and no handoff. Any weakened error result or digest/path/schema drift
exits 1. This deterministic contract is development evidence, not live-device
acceptance.

Generated bytes do not contain timestamps, random identifiers, host paths, or
environment-specific data. Identical arguments produce identical files.
Replacing placeholders with real material still requires secret review,
redaction, independent oracle review, parser and evaluator tests, the full rule
inventory, and authorized live-device acceptance.

## Generate static target scorecards

Generate one scorecard for every target already declared by the checked-in
supported-target contract:

```bash
mkdir -p reports
python3 scripts/generate-target-scorecards.py \
  --repo-root . \
  --output-dir reports/target-scorecards
```

`reports/target-scorecards` must not exist. The generator reads the supported
target contract, check pack, coverage manifest, scanner-profile source hashes,
and per-rule `validated_by` references. It checks target identities, counts,
content bindings, and check/coverage equivalence before writing anything.

Each schema-versioned scorecard visibly separates:

- the full benchmark, reviewed profile, implemented automated, manual,
  unsupported, not-applicable, and outside-profile counts;
- unavailable technically-automatable and collection-error denominators, which
  remain JSON `null` instead of being converted to zero;
- static validation references from executed validation evidence;
- release-gate measurements from values that the current metadata cannot
  establish; and
- each automation's reviewed `implementation_class` and
  `introduction_release`, plus the declarative/new-automation ratio for the
  current release line (the denominator and ratio remain `null` if any needed
  classification is unknown); and
- support, live-acceptance, and Evaluate-STIG comparison claims, all of which
  remain false.

After protected release evidence has been assembled, its repository-relative
metadata can be included explicitly:

```bash
python3 scripts/generate-target-scorecards.py \
  --repo-root . \
  --release-evidence release-evidence/v0.3.0/release-evidence.json \
  --output-dir reports/v0.3.0-target-scorecards
```

The generator records the reported target gate, release tag, source digest,
and evidence reference. It deliberately does not authenticate the protected
workflow artifact, device custody, reviewers, or live result and therefore
still makes no live-acceptance or support claim. Release governance remains the
authority for those determinations.

## Tool verification

The tools have no third-party Python dependency. Run their focused tests and
syntax checks with:

```bash
python3 -m py_compile \
  scripts/adapter_tooling.py \
  scripts/scaffold-target-adapter.py \
  scripts/validate-adapter-contract.py \
  scripts/generate-target-scorecards.py
python3 -m unittest scripts.disa_corpus.tests.test_adapter_tooling -v
```

The tests cover byte determinism, create-new output behavior, path and name
rejection, placeholder failure, completed positive/finding/error replay,
fail-closed error enforcement, checked-in target denominators, automation
metadata and unknown preservation, source drift, and the rule that even
reported passing acceptance metadata never becomes a claim from the generator.
